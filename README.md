# 随行管家 · 酒店住客全旅程智能服务台

> 覆盖**入住前 / 入住中 / 离店后**三个阶段的酒店智能客服系统。
> 与普通客服机器人的区别在于：**它不止会回答，还要把事办成**——
> 客人说"送两瓶水"，系统的产出不是一段道歉，而是**一张有工单号、承接部门、承诺时限的工单**。

> **项目性质（先说清楚）**：本项目**基于一个课程项目二次开发**。
> LangGraph 编排骨架、MCP 工具层、长短期记忆的工程经验来自它；
> **住中这一段是新建的**（工单域、分级鉴权、阶段识别、门店维度、多跳链路、坐席台、全部评测体系）。
> 所有业务数据均为 **mock**，SLA 数值是**假设值**（待用行业惯例校准），**不是生产系统**。

---

## 它解决什么问题

酒店客服的真正痛点不是"答得不准"，而是**承诺不可追踪**——整个市场都停在
"已为您记录，会尽快处理"，客人不知道要等多久、有没有人来。

而把云平台客服的架构搬过来时，酒店有**四条结构性差异**，它们改变的是架构，不是文案：

| # | 差异 | 后果 |
|---|---|---|
| 1 | **客人就在现场**（穿着浴袍等送水） | 北极星指标从"回答准确率"变成**住中需求按时闭环率** |
| 2 | **数据源是 PMS**（封闭、多厂商） | PMS 适配层是一等公民（mock 阶段是 `pms_room_state` 镜像） |
| 3 | **中心动作是派单**而不是查询 | 需要真正的工单域：状态机 + SLA + 超时升级 + 完成回执 |
| 4 | **知识属于门店**（同一句"早餐几点"两家店答案不同） | 知识库、缓存键、鉴权、埋点都要带 `store_id` |

```

└───────────────────────────────────┬──────────────────────────────────────┘
```

### 三个值得单独看的机制

**① 分级鉴权（`auth_guard`）** —— 三段需要的凭据不同，因为"还认不认得这个人"不同：

| 阶段 | 凭据 |
|---|---|
| 公开信息（早餐几点、WiFi 密码） | 不看身份 |
| 入住中（送物、报修） | **房间级**：房号 + 姓氏 + 离店日 |
| 入住前 / 离店后（订单、发票、失物） | **订单级**：订单号 + 手机后四位 |

两条反直觉的设计：**入住中的客人查自己的订单只需房间级**（能说出房号姓氏离店日已经证明身份，
再要订单号就是过度鉴权）；**安全类报修允许先派单、后验证**（漏水漏电这类，延误的代价高于误派）。
含统一失败话术（不区分"房号不存在"与"姓氏不匹配"）与连续失败锁定（防房号枚举）。

**② 住中工单域** —— 6 个状态、7 类工单，SLA 与派单部门由**类别映射**决定且**不接受模型传参**
（否则模型会给自己发一个 24 小时的时限）。超时自动升级到值班经理；每次流转都落事件链，
用于计算"未接单 / 未完成 / 已失败 / 未完成回执"四类失败归因。

**③ 说了办了就必须有单** —— 模型会出现"口头建单"（回复里写"已为您创建工单"但没调用工具），
这比答错更危险，因为它**看起来成功了**。所以服务端有兜底：回复里出现承诺性措辞且库里没有单，
就补建一张并标记 `fallback`，兜底率本身就是可观测指标。

## 快速开始

### 一键启动（双击）

| 文件 | 用途 |
|---|---|
| **`工具\启动项目.lnk`** | 双击这个：起 PostgreSQL → 后端 :5000 → 前端 :5173，就绪后自动打开浏览器 |
| `工具\停止本地.cmd` | 双击停止（只结束 5000/5173，不动数据库） |

> 三个文件的编码规则不是随意定的：`.cmd` 必须 **CRLF + 内容纯 ASCII**
> （LF 换行会让 cmd.exe 每行少读几个字符），`.ps1` 必须 **UTF-8 带 BOM**。
> **文件名可以中文，文件内容里不要出现中文。**

### 手动启动

```powershell
# 一次性准备
Copy-Item backend\.env.example backend\agent\.env   # 填 DASHSCOPE_API_KEY / MILVUS_URI / MILVUS_API_KEY
python 工具\初始化数据库.py                          # 建表 + 种子数据
python 工具\重建知识库.py --ingest --rebuild         # 知识入库（51 个切片，需联网）
python 工具\灌入缓存.py --rebuild                    # 预置问答入缓存

# 启动
cd backend; python run.py            # 后端 :5000
cd web;     npm run dev              # 前端 :5173
```

**试一句**：`能送两瓶矿泉水吗？`（会先确认身份：房号 `1208` / 姓氏 `陈` / 离店日 `2026-09-18`）

### 验收与自检

```powershell
python 工具\自检.py --deep      # 依赖状态 + 当前生效的降级路径
python 工具\前端自检.py          # 页面是不是我们的、能不能编译、后端通不通
python 工具\端到端测试.py        # 客人链路 + 坐席台闭环（29 项）
python 评测\运行评测.py          # 七个题集（117 个检查点）
python 工具\性能基准.py          # 固定题性能对比
```

## 评测

七个题集、共 **117 个检查点**，每题集都回答一个具体问题：

| 题集 | 检查点 | 它回答的问题 |
|---|---|---|
| A 门店差异 | 20 | 同一句话在两家店会不会答错店？ |
| B 越权与鉴权 | 20 | 越权能不能拦住？正当需求会不会被误挡？ |
| C 阶段与路由 | 30 | 三段场景的路由准不准？ |
| D 工单场景 | 15 | 类别/部门/SLA 对不对？坐席台能不能闭环？ |
| E 多轮连续性 | 13 | 会不会让客人重复提供信息？ |
| F 跨阶段 | 15 | 入住前/中/后要的凭据是不是真的不同？ |
| G 多跳与工作流 | 4 | 多跳真的发生了吗？超时真的会升级吗？ |

评测机制里有一条刻意的取舍：**失败用例自动重跑，重跑通过会标 `flaky` 但不算通过**，
汇总时"首次通过率"与"稳定通过率"两个数一起报——只报一个会误导决策。
结果文件**追加不覆盖**（`评测/评测结果_*.csv`），并落库 `eval_runs`（含环境快照）。

完整分析、逐条失败归因与诚实边界见 **[评测报告](评测/评测报告.md)**。

## 项目结构

```
hotel-agent/
├── backend/
│   ├── app/          FastAPI：router / service / infra / schemas
│   ├── agent/        LangGraph：agents / core / tools / mcp_servers / config
│   ├── database/     schema.sql · seed_hotel_ops.sql
│   ├── mock_data/酒店知识/{集团,门店}/   语料（集团 5 份 + 门店 2 份）
│   └── tests/        单元自测（工单 23 项 · 会话与鉴权 20 项）
├── web/              前端：住客端 + 坐席台（共用一份 api.ts）
├── 工具/             18 个脚本（启动 / 自检 / 初始化 / 数据维护 / 文档导出）
├── 评测/             题集 · 运行器 · 报告 · 历史结果
└── logs/             运行日志（不入库）
```

**数据库 23 张表**，分四类：业务主数据（orders / room_types / hotels …）·
门店与房态（store_facts / pms_room_state / lost_found_items）·
会话与工单（guest_sessions / stay_context / work_orders / work_order_events / auth_attempts）·
记忆与治理（short_term_memory / member_preferences / knowledge_chunks / answer_log / eval_runs …）。

## 技术栈

| 层 | 选择 | 为什么 |
|---|---|---|
| 编排 | LangGraph | 条件边与状态共享现成；本项目要加的是**节点**，不是框架 |
| 大模型 | DashScope qwen-plus | 中文与 function calling 稳定，一个 Key 覆盖生成 + 向量化 |
| 向量库 | Zilliz 托管 | 已跑通、免运维；**免费版只有 5 个集合名额**，所以加字段只能同名重建 |
| 业务库 | PostgreSQL | 事务一致；短期记忆与会员偏好都落这里（不走向量库） |
| 工具层 | MCP + 进程内工具**分层** | 有副作用的走 MCP（便于审计与身份注入），只读检索留进程内（少一次往返） |
| 后端 | FastAPI + SSE | 对话是单向流；坐席台动作频率低，轮询 + POST 足够 |
| 前端 | Vue 3 + Element Plus | 住客端与坐席台共用一份接口封装 |

## 已知边界（跑通 ≠ 可直接投产）

| # | 边界 |
|---|---|
| 1 | **数据全部是 mock**：订单、房态、门店事实、失物台账都是造的 |
| 2 | **SLA 是假设值**（送物 20 / 报修 30 / 安全类 10 分钟），行业惯例待核实 |
| 3 | **不接真实 PMS**：只做读 + 申请，`pms_room_state` 是 mock 镜像 |
| 4 | **无员工登录**：坐席台接口目前是开放的，上线前必须补账号/SSO + 按门店与部门授权 |
| 5 | **知识检索与生成依赖云端**（Zilliz + DashScope）：断网时降级为本地关键词检索并打标记，**不能完全离线** |
| 6 | **性能**：首字 p50 约 8 秒；多跳题集 p50 约 22 秒（多跳把一次 LLM 处理变成两次） |
| 7 | 前端**没有自动化 UI 测试**：`type-check`/`build`/前端自检都验了，"看起来对不对"仍需人打开看 |
| 8 | 不做公网部署、语音/电话、OTA 直连、支付与退款执行 |
